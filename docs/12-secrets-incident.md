# 12. Incident report: secrets committed to git history

**Status:** Closed. Secrets rotated, history rewritten, clean state verified. One residual noted
in section 5a: GitHub still serves the pre-rewrite commit by direct SHA, which is harmless
because the credentials it contains are dead.
**Severity:** Low actual, Medium-high had this been a real deployment.
**Found:** during a post-build repository audit, by inspecting what git was actually tracking
rather than trusting the `.gitignore`.

Written up as a real incident report because that is what it is, and because a finding you
discovered in your own work and handled properly is worth more than a clean-looking repo.

---

## 1. Summary

The repository's `.gitignore` excluded `*.db` and `*.db-journal` but not `*.db-wal` or
`*.db-shm`. SQLite runs in WAL mode in this project (set deliberately in
[`core/db.py`](../core/db.py) for concurrency), and WAL files contain **real database pages**.

A 1.7 MB `sentinelfloor.db-wal` was therefore committed and pushed to a public GitHub
repository, containing:

| Material | Count |
|---|---|
| PBKDF2-HMAC-SHA256 password hashes | 26 |
| Camera ingest keys (HMAC keys authenticating all detection input) | 6 of 6 |
| Duress fob shared secrets (authenticating the life-safety panic button) | 3 of 3 |

The `.db` file itself was correctly ignored. Only the sidecar leaked, which is exactly why it
was easy to miss: a casual check for tracked `.db` files returns nothing.

---

## 2. Root cause

Two contributing factors, and the second is the more interesting one.

**Proximate cause.** An incomplete ignore pattern. `*.db` does not match
`sentinelfloor.db-wal`, because the filename ends in `-wal`, not `.db`.

**Contributing cause.** A verification step that confirmed the wrong thing. The build was
checked with:

```bash
git ls-files | grep -iE "\.env$|secrets/|\.db$|\.venv|\.pem$|\.key$|credentials"
```

That returned clean, and the conclusion drawn was "no secrets tracked". The pattern was
anchored with `\.db$`, so it could not match the sidecars. **The check confirmed the absence
of the filenames I thought of, not the absence of secrets.**

This is the more useful lesson. A negative result from a check is only as good as the check's
coverage, and a control that validates your assumptions rather than the property you care about
gives false assurance. The correct check is content-based, not filename-based.

---

## 3. Impact assessment

**Actual impact: low.**

- All affected material was generated by `python -m core.seed` for a local demonstration.
- The system has never been connected to a real camera, a real store, or real staff accounts.
- No customer or employee personal data was involved, because none has ever entered the system.
- Password hashes were PBKDF2-HMAC-SHA256 at 600,000 iterations over randomly generated
  three-word passphrases. Not practically crackable.
- The camera keys and fob secrets only authenticate against a service bound to `127.0.0.1` on
  one laptop.

**Impact had this been a live deployment: medium-high.**

- Camera ingest keys let an attacker forge or suppress detection events at will (risk R-02).
- Duress fob secrets let an attacker trigger false alarms or, via counter desynchronisation,
  **silently disable the panic button** (risk R-08). That is a life-safety control.
- Password hashes are offline-crackable given time, and staff reuse passwords.

This maps directly onto risk **R-07** in [`03-threat-model.md`](03-threat-model.md), which
already recorded that secrets are stored in plaintext in the database and that this needs a KMS.
The register anticipated the exposure path; the ignore rule is what turned a known weakness
into an actual leak.

## 5. Remediation

### Completed

1. **Ignore rules corrected**, with an explanatory comment so the reason survives.
2. **Files untracked** from the index.
3. **Every exposed credential rotated.** All six camera keys, all three fob secrets, and all
   four account passwords are new. The leaked values are now dead.
4. **Rotation verified programmatically**: the current contents of
   `secrets/edge_credentials.json` and `secrets/duress_devices.json` were searched for across
   every blob in every commit. Zero matches.

Because the leaked credentials are dead, the exposure is contained even though the blob is
still present in history.

### 5. History rewritten and force pushed — completed

A backup bundle of the pre-rewrite state was taken first
(`git bundle create ... --all`), then history was rewritten to remove both sidecars from every
commit:

```bash
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch --force --index-filter \
  'git rm --cached --ignore-unmatch -q sentinelfloor.db-wal sentinelfloor.db-shm' \
  --prune-empty -- main

rm -rf .git/refs/original
git reflog expire --expire=now --all
git gc --prune=now
git push --force-with-lease origin main
```

`git filter-branch` rather than the recommended `git filter-repo`, because the latter was not
installed and this repository is trivial for the purpose: six commits, one branch, no tags, no
submodules. `--force-with-lease` rather than `--force`, so the push aborts if the remote moved
unexpectedly.

Scoped to `-- main` rather than `-- --all` deliberately. Rewriting `refs/remotes/origin/main`
too would have made `--force-with-lease` compare against an already-rewritten value, defeating
the safety check.

**Verified after the rewrite:**

| Check | Result |
|---|---|
| Commits preserved | 6 of 6 |
| Objects named `db-wal` / `db-shm` anywhere | 0 |
| Blobs containing the `pbkdf2_sha256$600000$` hash format | 0 |
| Original blob SHAs still present locally | purged |
| Working tree, `.env`, `secrets/`, database | intact |
| Test suite | 188 passing |
| Fresh clone from GitHub | 75 files, 6 commits, no database, no secrets |

## 5a. Residual: GitHub retains the unreferenced commit

Confirmed by probing from a clean clone: the pre-rewrite commit is **still retrievable from
GitHub by direct SHA**, even though it is reachable from no ref and absent from any clone.

```bash
git fetch origin c1ff960916ed8c50aed800b4ddb9a885d95cbcc1   # still succeeds
```

This is expected GitHub behaviour. Force pushing removes the ref; it does not garbage collect
the objects, and GitHub keeps unreferenced commits accessible for an unspecified period.

**Why this does not matter here:** every leaked credential was rotated before the rewrite, and
the rotation was verified against every blob in history. Anyone retrieving that commit obtains
dead camera keys, dead fob secrets, and hashes of passwords that no longer exist.

**If complete removal is required**, two options:

1. Ask GitHub Support to run garbage collection on the repository. This is the documented route.
2. Delete the repository and push a fresh one. Fastest and most certain for a small repo with no
   stars, forks, issues, or external references. Loses nothing but the creation date.

Recorded rather than quietly omitted, because "we force pushed so it is gone" is a common and
incorrect assumption, and the gap between removing a reference and removing data is exactly the
kind of thing this report exists to capture.

## 6. Prevention

| Control | Action | Status |
|---|---|---|
| Correct ignore patterns for all sqlite sidecars | Done, with a comment explaining why | Done |
| Content-based secret scanning in CI, not filename-based | Add `gitleaks` or `trufflehog` as a pre-commit hook and a CI gate. This is the control that would actually have caught it | **To do** (folds into phase 2 CI work in [`07-roadmap.md`](07-roadmap.md)) |
| Keep generated secrets out of the repository tree entirely | `secrets/` is gitignored and mode 0600, but a directory outside the working tree, or a real secret store, is stronger | **To do** (R-07 fix: KMS) |
| Move the database out of the working tree | Point `SENTINEL_DATABASE_URL` at a path outside the repo so no sidecar can ever be created next to tracked files | **Recommended** |
| Verify the property, not the assumption | Audit checks should search blob *contents* for known secret values, as step 8 did | Adopted |

### Recommended pre-commit hook

```bash
# .git/hooks/pre-commit
#!/usr/bin/env bash
if git diff --cached --name-only | grep -qE '\.(db|sqlite3)(-wal|-shm|-journal)?$'; then
  echo "Refusing to commit a database file or sqlite sidecar." >&2
  exit 1
fi
```

## 7. What this is worth saying in an interview

Do not hide it. It is a better story than a clean repo.

> I audited my own repository after finishing the build and found I had committed a SQLite WAL
> file to a public repo. It held 26 password hashes, all six camera HMAC keys, and all three
> duress fob secrets. My `.gitignore` covered `*.db` but not `*.db-wal`, and WAL files contain
> real database pages.
>
> The part I found most instructive was why my own check missed it. I had grepped tracked files
> for `\.db$`, which is anchored, so it could not match a file ending in `-wal`. The check
> confirmed the absence of the filenames I had thought of rather than the absence of secrets.
> That is a false-assurance failure, and it is the kind that worries me more than the original
> mistake.
>
> Impact was low, since these were local demo credentials for a system that has never touched a
> real camera. I rotated everything anyway, verified the rotation by searching every blob in
> history for the new values, fixed the ignore rules, and wrote it up. The control I am adding
> is content-based secret scanning in CI, because that is what would actually have caught it
> rather than a better-spelled filename pattern.

That answer demonstrates auditing your own work, correctly assessing severity without either
panicking or minimising, rotating before cleaning up, and identifying the second-order failure
in your own verification. All four are things interviewers are actually trying to find out.
